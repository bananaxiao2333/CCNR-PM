# 05 · 与 CCNR-RP 的对局对接

> 面向：接手本仓库的人、以及需要判断「对局页签为什么是空的」的管理员。
> 读完应能回答三件事：**数据从哪来**、**改动该落在哪一层**、**对方没装/改了签名时会怎样**。

---

## 1. 定位

管理面板的「对局管理」与「当局事件」两个页签，让管理员**不离开 PM** 就能：

- 看当局状态：是否运行中、当前模式、第 n/m 幕与剩余时间、正在跑哪些事件；
- 切幕（下一幕 / 切到指定幕）；
- 强制触发 / 结束某个事件；
- 收束对局、重开一局、只播结束动画；
- 看**当局事件流**（击杀、死亡、阶段推进、事件启停、结算……）。

对应 CCNR-RP 那边已有的管理能力（`/rp phase`、`/rp event`、`/rp end`、`/rp data events`），
本模组**没有新造任何对局规则**——只是把同一批入口搬到管理员本来就在用的面板里。

---

## 2. 硬性约束：PM 不直连数据服务器

用户明确要求的路线是：
**CCNR-RP 是唯一与 CCNR-Data（数据服务）通信的一方；PM 通过 CCNR-RP 取数，不建第二条 gRPC 客户端。**

理由不是省事，而是**权威源只能有一个**：

- 事件流、match_id、上报队列都是 CCNR-RP 的运行时状态。PM 自己再连一次数据服务，
  拿到的会是「数据库里已落盘的部分」，与管理员眼前这一局可能**不是同一批数据**
  （队列还没投递、或上一局的尾部还在重放）。两个数字并排显示却对不上，比只显示一个更糟。
- 等级显示已经定下「必须由数据服务确认过才显示」（CCNR-RP docs/19）。若 PM 绕开 CCNR-RP 直接读库，
  等于给同一份数据开了第二个出口，规则就守不住了。

因此：**PM 侧没有任何网络客户端、没有 protobuf、没有 gRPC 依赖**，只有反射。

---

## 3. 数据流

```
                    PM 客户端                                   CCNR-RP（服务端）
  ┌───────────────────────────────────┐
  │ 对局页签 / 事件页签                │
  │   ▲ 每帧读缓存                     │
  │   │                                │
  │ ClientMatchState（最近一份快照）   │
  │   ▲                                │
  │   │ MatchStateS2C（JSON）          │
  └───┼────────────────────────────────┘
      │ RequestMatchStateC2S（空载荷，面板打开期间每秒一次）
      ▼
  PmServerHandlers.onRequestMatchState ── 鉴权 ──► RpBridge.matchSnapshot()
                                                        │ 反射
      ┌─────────────────────────────────────────────────┘
      ▼
  EventManager.matchStatePayload()   对局状态（原样内嵌）
  EventManager.clock().phases()      幕表
  EventManager.events()              事件表 + 状态
  DataLink.recentEvents()            当局事件流（与 /rp data events 同源）

  对局动作：MatchActionC2S ── 鉴权 ── 白名单映射 ──► RpBridge.matchAction()
                                                        │ 反射
      switchPhase / triggerEvent / endEvent / end / gameOver / clearAll
```

要点：

- **一次往返给两块页签用**：`MatchStateS2C` 里同时含对局状态与事件流，
  两个页签读同一份快照，因此在同一帧里它们的读数必然一致。
- **快照是整体替换**：不做增量。这一份数据很小（几十 KB 上限），而增量合并要维护「哪条是新的」，
  一旦算错就出现「事件流里少一条击杀」这种没人会立刻发现的失真。
- **动作后一定回推新快照**：客户端**从不自己改本地状态**（切幕成功后不手动把「当前幕」改掉），
  否则「本地以为切幕了、对方其实拒绝了」这类不一致永远无从察觉。

## 4. 反射面：调用对方的哪些方法

`integration/RpBridge` 是**唯一**接触 CCNR-RP 的地方（另见 §7 的降级规则）。
读的部分：

| 对方入口 | 用途 | 读不到时 |
| --- | --- | --- |
| `EventManager.matchStatePayload()` | 对局状态（运行中/模式/当前幕/倒计时/进行中事件） | 空对象 → 界面显示「空窗期」，不炸 |
| `EventManager.clock().phases()` | 幕表（可切换的全部幕） | 空表 → 只显示当前幕（来自 matchState），切幕按钮置灰 |
| `EventManager.events()` | 事件表 + 状态 + enabled | 空表 → 只显示运行中的事件，触发按钮置灰 |
| `DataLink.recentEvents()` | 当局事件流 | 空表（数据服务未启用时属正常，不是错误） |

写的部分只认**六个白名单入口**（`RpBridge.matchAction` 的 `case`）：

| 网络动作 id | 对方入口 | 参数 |
| --- | --- | --- |
| `match_phase` | `switchPhase(String)` | 幕 id；**空串 = 下一幕** |
| `match_event_on` | `triggerEvent(String)` | 事件 id |
| `match_event_off` | `endEvent(String)` | 事件 id |
| `match_end` | `end(String)` | 收束理由（**服务端常量，不来自客户端**，见 §5） |
| `match_game_over` | `gameOver()` | — |
| `match_reset` | `clearAll()` | — |

**为什么是白名单**：`rpMethod` 最终来自网络包。即使 `PmServerHandlers` 已经把动作 id 映射过一遍，
在反射层再收一次口只花六行 `case`，却把「一个字符串参数就能调用对方任意公开方法」这条路径彻底关掉。

**为什么不在 PM 侧重校验参数**：「幕 id 存不存在」「事件现在能不能触发」都是**对方的规则**，
它自己会回绝并返回 `false`。在 PM 再判一次就是第二份校验，对方一改就漂移。PM 只负责把答案如实带回。

## 5. 信任边界

第三张权威链审计表（前两张见 [docs/02](02-举报工单.md) §4）：

| 客户端能送来的东西 | 服务端在哪里重新判定 | 依赖客户端自述？ |
| --- | --- | --- |
| 执行者身份 | **包里根本没有这个字段**——取自连接（`ctx.getSender()`） | 否 |
| 权限 | `PmServerHandlers.onRequestMatchState` / `onMatchAction` 第一步都是 `canAdminTicket` | 否 |
| 动作 id | `switch` 白名单；未知 id 明确回绝并提示（**不静默忽略**） | 否 |
| 幕 id / 事件 id（`arg`） | **不在 PM 侧校验**，原样交给 CCNR-RP 的入口，由对方回绝不可用的目标 | 否（只是线索） |
| 收束理由 | **不接受**：用服务端常量 `MATCH_END_REASON = "pm"` | 否 |

**为什么收束理由不接受客户端文本**：CCNR-RP 把它拼进事件上报的 JSON 载荷时用的是字符串拼接
（`"{\"reason\":\"" + reason + "\"}"`）。一段来自客户端的自由文本只要带一个引号，
就能把存进数据库的载荷弄成非法 JSON。面板上本来也没有理由输入框——
留一个「能传任意字符串」的口子只有坏处。

`PacketRegistrationTest.clientToServerSurfaceIsSmallAndReviewed` 把 C2S 包集合钉死成断言（当前 7 个）：
**新增 C2S 包必须同步更新本节与 docs/02 §4 的表**。

## 6. 界面

两个页签都**不持有 widget**（按钮是手绘 + 命中测试）：

- 对局快照**每秒刷新**。一旦页签持有 `EditBox`/`Button`，每次刷新都要 `clearWidgets()` 后重建，
  而那是**全局**的——会打断工单页签里正在输入的备注，症状是「备注打到一半光标没了」。
- `ClientMatchState.accept` 因此**刻意不调用** `PmAdminScreen.refreshIfOpen()`
  （`ClientTicketBoard.accept` 仍然调用它：工单数据只在动作后变，低频且需要重建）。

### 对局页签（`PmMatchTab`）

```
┌──────────────────────────────────────────────────────────────┐
│ 对局：进行中            模式：硬核生存                        │  ← 状态区固定四行
│ 当前幕：3/7 黄昏        计时：04:12                           │     第 4 行是错误行，
│ 进行中事件：空袭警报、物资投放                                │     始终占位不画字
│ （上一条动作的失败原因，红字；没有时不画）                    │
├───────────────────────────┬──────────────────────────────────┤
│ // PHASES                 │ // EVENTS                        │
│ 1  黎明                   │ 空袭警报              进行中      │
│ 2  黄昏  (当前)           │ 物资投放              待触发      │
│ 3  深夜                   │ 已停用                待触发      │
│                           │                                  │
├─────────────┬─────────────┼──────────────────────────────────┤
│  下一幕     │  切到此幕   │        触发事件 / 结束事件        │
├─────────────┴─────────────┴──────────────────────────────────┤
│    收束对局    │    重开一局    │      结束动画                │
└──────────────────────────────────────────────────────────────┘
```

- **状态区固定预留四行**：错误行若出现时才撑高，下方两个列表会在管理员刚点完按钮的瞬间整体跳一下，
  鼠标还在原处，很容易误点到刚移到指针下的另一行。
- **「触发 / 结束」是一个按钮**：目标事件的状态决定它是哪一件。拆成两个按钮只会让其中一个
  在大多数时候是灰的（事件要么待触发、要么在运行）。
- **亮底必须是深字**：选中行（`selectedBar`）不给状态上色——
  docs/03 §2 那条硬性约束优先于配色。
- 按钮可用性**只是体验**。真正的判定在 CCNR-RP 自己那里；被改造过的客户端照样发得动指令，
  但每一条都会在服务端与对方那侧被重新判定。

### 事件页签（`PmEventsTab`）

```
// EVENTS  共 37 条 · 最新在上
18:42:07  CHARACTER_KILL    A 击杀 B
18:41:55  PHASE_ADVANCED    阶段推进：黄昏
...
```

- **最新的一行在最上面**：这是一个开着面板盯的活数据源，管理员最常问的是「刚才发生了什么」。
  正序意味着每来一条新事件都要往下滚。
- 时间用 `TimeText.clock`（`HH:mm:ss`）而不是 `TimeText.format`（`yyyy-MM-dd HH:mm`）：
  一局对局里的击杀都发生在同一天，日期占掉一半宽度却提供零信息，挤掉的正是事件正文；
  而「秒」在这里是必需的——同一分钟内的连续击杀要靠它排先后。
- **数据服务掉线时这个页签照样有内容**：事件流是 CCNR-RP 的本地环形缓冲，
  可见性刻意不依赖连通性（对方 docs/19）。「上报没上去」与「看得见发生了什么」是两件事，
  把它们绑在一起会让管理员在最需要看事件的故障时刻恰好什么都看不到。

### 轮询

- 面板**打开时**取一次（不取的话切到对局页签会先看到一秒的「正在读取……」）。
- 打开期间，**前台是「对局 / 事件」时每秒取一次**；前台是「工单管理」时不取
  （工单是低频管理数据，动作后由服务端回推；给它也挂轮询只会白费流量）。
- 面板关闭即停。不订阅 CCNR-RP 自己的推送包——那要依赖对方的协议细节，
  为省每秒一个空载请求不值得。

## 7. 降级规则（对方没装 / 改了签名）

| 情况 | 表现 |
| --- | --- |
| 服务端没装 CCNR-RP | 快照是 `{"available":false}`（**正常载荷**，不是错误）→ 两个页签各显示一行「服务端没有安装 CCNR-RP」，所有按钮置灰；`canAdminTicket` 之外**没有任何异常** |
| 对方装了但还没初始化完（`CCNRRPMod.eventManager == null`） | `matchSnapshot()` 返回 `null` → 同上；下一次轮询会自愈 |
| 对方改了某个方法签名 | 该**块**降级：例如 `clock().phases()` 读不到 → 幕表为空、只显示当前幕，其余照常。四块（match / phases / events / log）各自独立降级，一块失败不会让整份快照变空 |
| 数据服务未启用 | 事件流为空，其余照常（数据服务与对局可见性无关） |
| 客户端没装 PM / 版本不匹配 | `PmChannel.sendTo` 静默跳过，服务端功能不受影响 |

**「装了就调用对方的唯一入口、没装就退回原版语义」**是本仓库对其它模组的一贯约定
（另见 `client.RpPanel`、`integration.RpBridge` 的角色/刷人部分）。

## 8. 怎么排查「对局页签是空的」

按顺序看四件事：

1. **服务端装 CCNR-RP 了吗**：页签第一行直接写着。装了却显示「未安装」→ 看服务端日志有没有
   `[CCNR-PM] 读取 CCNR-RP 事件管理器失败`。
2. **权限**：接口与动作都走 `canAdminTicket`（OP≥2 或权限节点 `ccnrpm.admin.ticket`）。
   没权限的客户端连面板都打不开（`PmClientState` 是 fail-closed 的）。
3. **事件流有内容吗**：如果对局状态正常、事件页签一直空，那是**本局还没有事件**——
   事件流是人家的运行时缓冲，重开一局会清空（换 match_id）。
4. **动作点了没生效**：看状态区第 4 行的红字。常见的是「目标已变化或当前不可用」
   （例如事件已经在运行、或幕 id 在对局中被重载掉了）——这是 CCNR-RP 的回绝，不是 PM 的判定失败。

## 9. 已知边界

1. **只读 + 六个动作，没有「新建/编辑事件定义」**。定义属于配置文件（`config/ccnr_rp/*.json`），
   本模组按约定不碰对方的配置文件（`AGENTS` 硬性禁令：变更限本仓库）。
2. **事件流最多 120 行**（取最新）。对方的内存缓冲默认 200 行；面板一次也就显示十几行，
   而载荷超出 `writeUtf` 上限的表现是「打开面板什么都不发生」，是最难定位的一类缺陷。
   单行正文截断到 240 字符。
3. **不显示「谁上报成功了」**。上报队列的状态在 CCNR-RP 的 `/rp data status` 里；
   本模组刻意不复制那份数据——复制出来的必然是滞后的第二份读数。
4. **轮询是 1 秒**。比这更密没有意义（倒计时的精度由本地时钟保证），更疏会让事件流看起来是死的。
5. **没有实机验证记录**。渲染与输入逻辑只能由用户实机确认；可测的部分
   （快照解析、派生读数、页签注册一致性）已抽成纯类并覆盖（`MatchSnapshotTest`、`PmAdminTabsTest`）。
