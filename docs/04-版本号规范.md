# 04 · 版本号规范

> 本规范从 CCNR-RP 的 **193 个历史版本**里反推出来（不是凭空发明），
> 再据此为 CCNR-PM 定死规则：**编号规则与 CHANGELOG 标题写法都以 CCNR-RP 为准**。
> 改动版本号前先读本文。

---

## 1. 格式

```
<主版本>.<功能批次>.<修订号>
   0..n      1..n       0..n
```

三段都是数字，形如 `0.1.0`、`2.18.43`、`1.5.29`。

**这不是严格 SemVer**：SemVer 的 minor 是「向后兼容的新功能」，取值范围小；
本规范的中段是**功能批次计数器**，可以涨到几十（CCNR-RP 出现过 `2.18.43`）。
把它当 SemVer 会得出「minor=18 意味着 18 次破坏性变更」这种错误结论。

| 段 | 含义 | 何时 +1 |
| --- | --- | --- |
| **主版本** | 项目世代 / 架构换代 | 极少动。CCNR-RP 193 个版本里只出现过 `0`、`1`、`2` |
| **功能批次** | 一批新功能 / 一次迭代 | 每次交付一批新功能 +1，**并把修订号归零** |
| **修订号** | 同一批次内的修复 | 修 bug、调文案、改样式等不改接口的改动 +1 |

### 主版本的含义（重要）

| 主版本 | 含义 | 证据（CCNR-RP） |
| --- | --- | --- |
| `0` | **开发期**，尚未对外正式发布 | `0.1.0 → 0.2.0 → … → 0.9.0`（中段逐个迭代 +1，没有修订号） |
| `1` | **首个正式版及其迭代** | `1.0.0` 为「首个正式版」，之后 `1.0.1`、`1.1.0`… |
| `2+` | 架构换代 | `2.0.0` 起为第二代实现 |

`0.x` 阶段**中段每迭代一次 +1、末段恒为 0**——CCNR-RP 的 0.x 期没有任何 `0.1.1` 这类版本。

---

## 2. 本项目当前版本

**`0.13.0`** —— 符合上表：本模组仍处于开发期（主版本 `0`），
`0.x` 阶段**中段每迭代一次 +1、末段恒为 0**（与 CCNR-RP 的 0.x 期一致，见 §6）。

> 什么时候升到 `1.0.0`：**完成一次真实游戏内验证之后**。在这之前主版本保持 `0`。
> 这与 CCNR-Com 的做法（直接以 `1.0.0` 作为首个正式版）不冲突——
> 它是「已验证并发布」的版本，而本项目当前还差这一步。

---

## 3. 单一真源与必须同步的三处

**唯一真源**：`gradle.properties` 的 `mod_version`。jar 名、`mods.toml` 的版本都从它派生。

| 位置 | 内容 | 说明 |
| --- | --- | --- |
| `gradle.properties` | `mod_version=0.13.0` | **真源**。改版本只改这里 |
| `CHANGELOG.md` | 顶部条目 `## 0.13.0（<摘要>）` | 必须与真源一致（写法见 §6） |
| `README.md` | 「当前版本：\`0.1.0\`」一行 | 必须与真源一致 |

`src/main/resources/META-INF/mods.toml` 写的是 `version="${file.jarVersion}"`，
**由构建从 `mod_version` 注入**，因此不必（也不应）手工维护第二个版本号——
两份手写版本号迟早会不一致，而那种不一致只有玩家装错版本时才会暴露。

---

## 4. 交付流程（每次改动都要走）

```
实现 → 验证（spotlessApply && build && test -PrunTests）
     → bump mod_version      ← 判断是「批次」还是「修订」
     → CHANGELOG 顶部补条目
     → README 当前版本同步
```

**为什么每次改动都 bump**：本模组没有热更新通道，玩家判断「我装的是不是修好的那版」
只能靠版本号。改了却不 bump，等于让玩家无法区分修前修后。

**为什么不能只改 jar 不改 CHANGELOG**：版本号脱离了条目就只是一串数字，
无法回答「这版修了什么」——而这是玩家唯一真正关心的问题。

---

## 5. 门禁

`VersionConsistencyTest` 会拦住版本漂移，它检查三件事：

1. `gradle.properties` 的 `mod_version` 形如 `<数字>.<数字>.<数字>`
2. `CHANGELOG.md` 里**第一个带版本号的标题**与真源一致（防止「改了真源忘了写条目」）
3. `README.md` 中出现该版本号（防止「改了真源忘了同步文档」）

门禁只校验**同步关系**，不锁死标题写法，因此 CHANGELOG 用
`## [0.1.0] - 摘要` 还是 `## 0.1.0（摘要）` 都能通过（见第 6 节）。

## 6. 与其它 CCNR 仓库的对照

| 仓库 | 当前版本 | 起始版本 | CHANGELOG 标题写法 |
| --- | --- | --- | --- |
| CCNR-RP | `2.26.12` | `0.1.0` | `## 2.26.12（主题摘要）` |
| CCNR-Com | `1.1.0` | `1.0.0` | `## [1.1.0] - 标题` |
| **CCNR-PM**（本仓库） | `0.13.0` | `0.1.0` | `## 0.13.0（摘要）` |

**编号规则三个仓库一致**（都是从 CCNR-RP 那 193 个版本反推出的同一套）。

**标题写法也已对齐 CCNR-RP**（`## <版本>（<摘要>）`）：本仓库原先用
`## [版本] - 标题`（Keep a Changelog 风格），与 CCNR-RP 不一致；现已改为与 CCNR-RP 完全相同的写法，
因此同一家族里两个仓库的 CHANGELOG 可以用同一套眼光扫读。
CCNR-Com 仍是 `## [版本] - 标题`（本次不改动其它仓库，各自有独立的 AGENTS 约束）。

> 历史条目**只改标题格式、不改措辞**：CHANGELOG 是给玩家看的既成记录（见 §7）。
> 因此少数标题会因原来的正文自带括号而出现嵌套的全角括号，属格式迁移的正常结果。

---

## 7. 边界与反例

- **允许跳号，不回溯补齐**：CCNR-RP 缺 `1.0.3`、`2.18.25`。跳号通常来自
  「一次提交合并了两个迭代」；事后补一个空条目毫无价值。
- **不改写已发布的历史条目**：CHANGELOG 是给玩家看的既成记录。发现旧条目写错，
  在新条目里更正，不回头改。
- **不为了「好看」刻意凑 `x.0.0`**：修复就是修复，批次号不该为叙事服务。
- **版本号不参与任何逻辑判断**：不要写「版本 ≥ 2.1 才启用某功能」这类判断——
  存档里没有版本戳，从旧版本升上来的世界会走错分支。
  要做兼容就按**数据结构是否存在**判断（本项目的做法：`DbSchema.VERSION` 管表结构，
  与 mod 版本号完全解耦）。
