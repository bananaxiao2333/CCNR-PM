# 00 · 总览

> CCNR-PM 的架构、包布局、数据流与模块边界。改动代码前先读本文。

---

## 1. 定位

**CCNR-PM** 是面向服务器的**玩家管理模组**，第一个功能是举报工单。

与另外两个 CCNR 仓库的关系：

| 仓库 | 关系 |
| --- | --- |
| CCNR-RP | **无依赖**。共用界面视觉语言与工程规范，代码互不引用 |
| CCNR-Com | **可选依赖**（`mandatory=false`, `ordering=AFTER`）。提供 `/a` 命令供本模组接管 |
| CC-api | 无关 |

**为什么坚持独立**：玩家管理是横切关注点，任何服务器都可能只想要它而不想要 RP 规则系统。
反过来，本模组的任何改动也不需要动另外两个仓库。

## 4. 存储分层

| 层 | 路径 | 用途 |
| --- | --- | --- |
| serverconfig | `world/serverconfig/ccnr_pm-server.toml` | 调参（长度/冷却/并发） |
| 可编辑定义 | `config/ccnr_pm/report_categories.json` | 管理员可改的举报类别 |
| 后端配置 | `config/ccnr_pm/db.properties` | 数据库开关与连接 |
| 运行时数据 | `world/ccnr_pm/tickets.json` 或数据库 | 工单 |
| 头像缓存 | `config/ccnr_pm/avatars.json` | 服务端抓来的头像（base64，新覆盖旧） |
| 见过的玩家 | `config/ccnr_pm/known_players.json` | 关联玩家合法性（在线 或 见过面）+ 离线玩家的 UUID |

JSON 一律**原子写**（`.tmp` + `ATOMIC_MOVE`），损坏时备份 `.bak` 并继续运行，不因单文件损坏停摆。

## 5. 生命周期

```
mod 构造期
  ├─ registerConfig(SERVER, PmConfig.SPEC)
  ├─ PmChannel.register()                      网络通道
  ├─ register(new AdminChatInterceptor())      命令接管（LOWEST 优先级）
  ├─ addListener(PmPermissions::onGatherNodes) 权限节点注册
  └─ addListener(PmCommand::onRegisterCommands) /pm 命令树

RegisterCommandsEvent（每次命令树重建，含数据包重载）
  └─ AdminChatInterceptor 重新接管 /a 与 /admin

PlayerLoggedInEvent
  └─ AvatarService.prefetch(该玩家)          头像预热（异步 HTTP，失败不影响登录）

ServerAboutToStartEvent
  ├─ AvatarService.init(configDir)            载入 avatars.json
  └─ TicketService.init(worldDir, configDir)
       ① 读 db.properties
       ② 若启用：连库 → 建表 → 成功则用 JdbcTicketStore
       ③ 否则/失败：用 JsonTicketStore（回退）
       ④ 载入举报类别（缺失则写模板，损坏则回退内置六类）

玩家执行 /a ──► 见 docs/02

ServerStoppingEvent
  ├─ TicketService.shutdown()  排空写队列 → 断开连接
  └─ AvatarService.shutdown()  强制落盘 avatars.json（对称清理）
```

## 6. 线程模型

| 谁 | 允许做什么 |
| --- | --- |
| 主线程（服务端） | 全部工单逻辑。`TicketService` 的每个方法都必须在主线程调用 |
| 主线程（客户端） | 全部界面逻辑。包处理器注册为 `consumerMainThread`，已在主线程 |
| `ccnr-pm-db-writer` 守护线程 | **仅** JDBC 写。绝不触碰 Level / 实体 / NBT / 网络 / 渲染 |
| `ccnr-pm-avatar`（2 线程） | **仅** HTTP 下载 + base64 编码。只接收主线程构造好的 `PlayerRef` 快照，绝不触碰实体；结果回主线程后才发包 |

数据库只有**一条连接 + 一把锁**。工单是低频写数据，连接池的复杂度换不来收益。

## 7. 网络协议

通道 `ccnr_pm:main`，协议版本 `"1"`。**注册顺序即协议编号**——新增包只能追加在末尾，
插在中间会让已发布客户端整体错位。

| # | 方向 | 包 | 载荷 |
| --- | --- | --- | --- |
| 0 | S2C | `OpenReportScreenS2C` | 预填内容、在线玩家名单、可选类别、长度上限 |
| 1 | C2S | `SubmitTicketC2S` | 关联玩家原始输入、类别 id、举报内容、详细描述 |
| 2 | S2C | `SubmitResultS2C` | 成功标志、工单短号、错误列表（JSON） |
| 3 | S2C | `TicketNoticeS2C` | 新工单通知（发给管理员）：短号/状态/类别/提交者/关联玩家/正文/头像 base64 表 |
| 4 | C2S | `RequestTicketsC2S` | 管理面板请求一页工单（筛选值 + 页码） |
| 5 | S2C | `TicketListS2C` | 一页工单数据（JSON，编解码见 `TicketPage`） |
| 6 | C2S | `TicketActionC2S` | 管理动作：认领 / 办结 / 驳回 / 忽略（工单 id + 备注） |
| 7 | S2C | `AdminResultS2C` | 动作结果（成功与否 + 失败原因语言键） |
| 8 | S2C | `OpenAdminPanelS2C` | 打开管理面板（空载荷，由 `/pm panel` 触发） |
| 9 | C2S | `PlayerActionC2S` | 看板头像上的玩家动作（动作 id + 目标 uuid/名字 + 参数如角色 id） |
| 10 | C2S | `RequestProfessionsC2S` | 空载荷：问服务端「有没有 CCNR-RP、有哪些角色」 |
| 11 | S2C | `ProfessionListS2C` | 是否有 CCNR-RP + 角色列表 JSON（`ProfessionRef`） |

约定：
- 消息类为 `PmPackets` 内的 `public static final class`；两个构造器（业务入参 / `FriendlyByteBuf`）；
  实例方法 `encode`；静态 `handle`。
- **长度上限以常量声明一次，编解码共用**。上限不匹配会造成缓冲区错位，且不会立刻报错，
  表现为「玩家名变成乱码」这类诡异现象。
- **动作 id 是字符串协议，两端共用 `PmPackets` 的 `ACT_*` 常量**：两端各写一份字面量，
  改一处忘一处的结果是「点了没反应」。`PacketRegistrationTest` 会断言「每个动作 id 在服务端都有分支」。
- S2C 处理器用 `DistExecutor.unsafeRunWhenOn(Dist.CLIENT, () -> () -> ...)` 双重 lambda 保护，
  服务端不会类加载客户端类。
- 客户端未装模组时 `PmChannel.sendTo` 静默跳过（服务端功能照常）。

## 8. 模块边界（不要打破）

1. **`TicketService` 是唯一的工单入口**。命令与网络包都必须经它，不要直接调 store。
2. **`ReportValidator` 是唯一的校验实现**。客户端预校验与服务端重校验必须调同一个函数——
   两边各写一份必然漂移，症状是「面板放行、服务端拒绝」。
3. **存储选择只看 `Database.usable()`**，不要用 `enabled()`。
   `enabled()` 表示「配置里打开了」，`usable()` 表示「真的连上了」。
3b. **头像 URL 必须过 `SkinUrl.isHttpUrl`**：URL 来自外部数据，
   不加协议白名单的话一个 `file:` URL 就能让服务端去读本机文件。
4. **`client` 包不得被服务端路径引用**（除 `DistExecutor` 的双重 lambda 内）。
5. **`PmTheme` 是唯一的颜色与绘制来源**，界面代码里不得出现裸 `0x` 色值。
6. **纯类不得引入 MC 依赖**，否则会失去离线单测能力。
7. **对其它模组的依赖只能是反射 + 降级**（`client.RpPanel`、`integration.RpBridge`）：
   不引用对方任何类，装了就调用对方的**唯一入口**，没装/签名变了就退回原版语义。
   绝不把对方流程抄一份进来——那会在对方改动后漂移，且症状极难归属。

## 9. 已知边界

1. **数据库不支持给已有表加列**。`DbSchema` 只做 `CREATE TABLE IF NOT EXISTS`；
   改列结构必须新增 `pm_schema_version` 迁移阶梯。
2. **`TicketService` 用静态单例**。符合「服务端只有一个工单系统」的现实，但意味着同进程内不支持多份实例
   （对 Forge 服务端不构成限制）。
3. **界面无独立单测**。可测的部分（断行、校验、类别、方言、存储）已抽出到纯类并覆盖；
   渲染逻辑只能靠人工验证。
4. **未做玩家自助查询工单**（数据具备，缺界面）。
