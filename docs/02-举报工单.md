# 02 · 举报工单

> 本模组的第一个功能，也是当前唯一面向玩家的功能。
> 本文写清「为什么这样设计」「边界在哪」「出问题怎么定位」。

---

## 1. 需求与动机

**需求原文（用户）**：

> 玩家用管理员发送消息那个命令不会显示无权限，而是直接打开一个工单面板
> （工单面板里面的举报内容填写玩家刚刚发送的消息内容），工单面板里面可以选择玩家（在线玩家），
> 然后填写举报类别，然后是填写举报详细描述，点击举报就能创建工单。
>
> —— 补充：要有**一个单独的命令**能直接打开工单界面；「被举报玩家」改叫**关联玩家**，
> 且像 autocomplete 那样**允许输入多个**；关联玩家与详细描述都是**选填**；详细描述要**长文本**。
> 有权限的管理员要在**聊天区收到提醒**，并在**左上角弹出一张 4:3 横版小卡片**（标题、描述过长自动换行/截断，
> 一排玩家头像，**提交者与关联者要区分**）；建单时**自动缓存头像的 base64**（全局共享、新覆盖旧），
> 因为是第三方服务器。

**现象**：玩家执行 `/a <消息>` 时，因为 CCNR-Com 用 Brigadier 的
`.requires(Permissions::canAdmin)` 注册该命令，**普通玩家执行它得到的是「命令不存在 / 无权限」**，
一腔想说的话直接被丢掉。

**设计意图**：把这个「被拒绝的动作」接住，转成一条**有结构的举报工单**。

- 玩家侧：不再吃闭门羹，想说的话有了去处，而且是一条能被管理员检索、跟踪、办结的记录。
- 管理侧：从「聊天里刷过去的一句话」变成「带类别、带对象、带状态的结构化工单」。

这比单纯把报错文案改温柔更有价值：**它把一个无意义的失败，变成了一条有用的数据。**

## 2. 命令接管的实现原理

### 2.1 为什么不改 CCNR-Com

本模组**独立于 CCNR-RP / CCNR-Com**，不产生任何编译期依赖（见 `docs/00`）。
`/a` 的所有权在 CCNR-Com，我们不去改别人的仓库。

### 2.2 怎么接管

Forge 在 `RegisterCommandsEvent` 把命令树交给各模组填充。Brigadier 的
`CommandNode.addChild` 以**名字为键**存放子节点，因此后注册的同名节点会**覆盖**先生成的：

```
CCNR-Com  : dispatcher.register(literal("a").requires(canAdmin).then(arg("message")...))   // NORMAL 优先级
本模组     : root.addChild(literal("a").executes(...).then(arg("message")...))              // LOWEST 优先级
```

时序由 `EventPriority.LOWEST` 保证（CCNR-Com 用默认的 NORMAL，NORMAL 先于 LOWEST 执行）。
见 `AdminChatInterceptor.onRegisterCommands`。

### 2.3 管理员的行为一点都没变

接管后管理员**必须照旧发管理通讯**。做法是：在覆盖前从原 `/a` 节点里取出
`message` 子节点的执行器（`Command<CommandSourceStack>`），管理员路径直接把命令上下文转交给它执行：

```java
if (PmPermissions.canAdminChat(player)) {
    if (originalMessageCommand != null) return originalMessageCommand.run(ctx);   // 原实现原样跑
    ...
}
```

因此广播范围、长度校验、失败提示全部沿用 CCNR-Com 的实现。
**我们只新增了「非管理员 → 开工单面板」这一条分支。**

原节点的其它子命令（若日后 CCNR-Com 给 `/a` 加了新分支）会被原样挂到新节点上，不会被抹掉。

### 2.4 别名 `/admin`

CCNR-Com 用 `Commands.literal("admin").redirect(adminCmd.build())` 注册别名。
**redirect 的目标在 `build()` 那一刻就固定了**，指向的是旧节点。
所以只替换 `/a` 是不够的——`/admin <消息>` 仍会走旧路径、仍会回绝普通玩家。
本模组因此额外把 `/admin` 重新指向新节点（仅当它确实是 `/a` 的 redirect 时才动它，
不会误伤别的模组注册的 `/admin`）。

### 2.5 判定「是不是管理员」

判据必须与 CCNR-Com 的 `Permissions.canAdmin` **完全一致**：
`OP ≥ 2` **或** 拥有权限节点 `ccnrcom.admin.chat`。

否则用 LuckPerms 单独授了该节点、但没有 OP 的管理员会被误判成普通玩家，
一执行 `/a` 就被导向举报面板——这是本功能最不能出的错。

CCNR-Com 的 `PermissionNode` 我们无法编译期引用，Forge 的 `PermissionAPI` 也没有按字符串查询的重载
（只有 `getPermission(ServerPlayer, PermissionNode<T>)`）。做法是运行时从
`PermissionAPI.getRegisteredNodes()` **按名字**找到该节点再用同一套 API 求值，见 `PmPermissions.adminChatNode()`。

### 2.6 边界（重要）

| 情况 | 行为 |
| --- | --- |
| CCNR-Com 已安装 | 接管生效，普通玩家开面板，管理员照旧 |
| CCNR-Com **未**安装 | `/a` 不存在，本模组**不会凭空创建它**（避免与别的模组抢同名命令）；只记一条 INFO 日志。举报面板仍可用 `/pm report` 打开 |
| 命令来自控制台/命令方块 | 没有玩家可弹面板，保持原行为 |
| 数据包重载 | 命令树整树重建，本处理器会重跑一次并重新接管（`installed` 标记只用于防止同一次构建里重复接管） |
| 存在同名的其它 `/a` | 我们按名字覆盖，可能影响对方。已在 `mods.toml` 声明对 ccnrcom 的 `AFTER` 可选依赖，正常情况下不冲突 |

## 3. 端到端数据流

```
玩家输入 /a 我今天被 Bob 用外挂打了
        │
        ▼
[客户端] 命令树里 /a 对所有人可见（requires 已被移除）
        │  发到服务端
        ▼
[服务端] AdminChatInterceptor.onMessage
        │  canAdminChat()? ──是──► 转交 CCNR-Com 原执行器（管理通讯，行为不变）
        │  否
        ▼
[服务端] TicketService.sendOpenPanel(player, "我今天被 Bob 用外挂打了")
        │  S2C OpenReportScreenS2C { prefill, 在线玩家名单, 可选类别, 长度上限 }
        ▼
[客户端] TicketScreen 打开
        │  举报内容 ← 预填 prefill（必填）
        │  关联玩家 ← 自由输入，逗号分隔可多个；输入时按在线名单补全（选填）
        │  举报类别 ← 从类别列表里选（必填）
        │  详细描述 ← 多行文本域（选填）
        ▼
[客户端] 本地用 ReportValidator 预校验（与服务端同一套规则）→ 通过
        │  C2S SubmitTicketC2S { targetName, categoryId, content, detail }
        ▼
[服务端] PmServerHandlers.onSubmitTicket
        │
        ▼
[服务端] TicketService.submit  ←── 信任边界，逐项重校验
        │  ① ReportValidator（类别启用/内容长度/关联玩家数量与名字长度）
        │  ② 解析关联玩家：在线者附 UUID，离线者只留名字（**不拒绝**）
        │  ③ 冷却与未办结并发上限
        │  ④ 落库（分配 UUID 标识）
        ▼
[服务端] S2C SubmitResultS2C { ok, label, errors }
        │
        ├─ 立即：私聊提醒在线管理员（持久、可回看）
        └─ 取头像 → 异步抓取（≤ timeoutMs）→ 回主线程
              └─ S2C TicketNoticeS2C { …, avatars }   左上角 4:3 卡片
        ▼
[客户端] 面板显示「已创建工单 #a3f2c1d8」，锁定表单，只留「关闭」
```

## 4. 信任边界：客户端说的都不算

面板上的本地校验**只为即时反馈**（避免「面板放行、服务端拒绝」的往返）。
真正的判定全部在 `TicketService.submit` 里重做：

| 校验项 | 为什么必须服务端做 |
| --- | --- |
| 类别存在且**启用** | 客户端可能拿着旧的类别列表；也可能被改造过 |
| 内容/描述长度 | 客户端的 `maxLength` 可被绕过 |
| 关联玩家**数量与名字长度** | 客户端可被改造，塞进几百个名字会撑爆工单 |
| 提交冷却 | 防刷；**纯服务端概念**，客户端面板不知道它的存在（`SubmitGate`） |
| 未办结工单上限 | 防止用大量工单淹没受理队列；同上 |

**关联玩家是选填的，但不再是「随便写」。** 两道判定（v0.11.0 起，用户要求）：

1. **格式**（`ReportValidator`，客户端与服务端共用）：只允许原版用户名字符（字母/数字/下划线）且 ≤16 位。
   刻意不照搬「正版至少 3 位」——第三方/离线服务器上短名字是真实存在的。
2. **合法性**（服务端权威，`player.KnownPlayers`）：**在线 或 本服见过面**才算合法，否则回绝并指名是哪个名字。

为什么判据不是「必须在线」：人刚下线、或已经改名，恰恰是最该能举报的时刻；而随手打一个
不存在的名字会变成一张指向空气的工单（管理员查不到人、也无从受理）。名录在每次登录时登记，
落盘 `config/ccnr_pm/known_players.json`，重启后仍然有效。离线但见过的玩家会补上 **UUID**，
因此看板头像也能按 uuid 命中缓存。

服务端与客户端共用**同一个** `ReportValidator`（纯类，无 MC 依赖），
从根上杜绝「两边规则不一致」这类最难排查的联机缺陷。

### 权威链审计表（逐项可核对）

**工单方面的攻击面只有 1 个 C2S 包**（`SubmitTicketC2S`），它是客户端唯一能影响**工单状态**的入口
（v0.9.0 新增的玩家动作包见本节末尾的表）：

| 客户端能送来的东西 | 服务端在哪里重新判定 | 依赖客户端自述？ |
| --- | --- | --- |
| 举报人身份 | **包里根本没有这个字段**——取自连接（`ctx.getSender()`） | 否 |
| 关联玩家名字 | `ReportValidator.parseTargets` 重拆 → `resolveTargets` 按**此刻**在线状态重解析 UUID | 否 |
| 举报类别 | `CategoryRegistry.isSelectable`（存在**且**启用） | 否 |
| 正文 / 描述长度 | `ReportValidator` + 服务端 `PmConfig.limits()` | 否 |
| 关联玩家数量与名字长度/字符集 | `ReportValidator` | 否 |
| 关联玩家**是否存在于本服** | `TicketService.submit` 用**在线名单 + `KnownPlayers` 名录**重判（包里的名字只是文本，服务端自己解析 UUID） | 否 |
| 提交频率 | `SubmitGate`（冷却）——客户端**完全不知道**这条规则 | 否 |
| 未办结并发数 | `SubmitGate`（上限）——同样客户端不可见 | 否 |
| 「我已校验过」 | **不存在这种输入**：`validate` 签名里没有 boolean 开关 | — |

三条被自动化门禁固定下来的结构性约定（`ServerAuthorityTest`）：

1. `SubmitTicketC2S` 的字段集合恒为 `{targetRaw, categoryId, content, detail}` ——
   一旦有人加入身份类字段，测试立刻失败（已实测会失败）。
2. `ReportValidator.validate` 的签名不得出现 boolean 参数 —— 防止「跳过校验」的口子。
3. 防刷规则只能在服务端判定（`SubmitGate` 是纯类，客户端不引用它）。

### 权威链审计表（v0.9.0 新增：看板头像上的玩家动作）

`PlayerActionC2S` / `RequestProfessionsC2S` 是**第二批**客户端能影响服务端的入口，
判据与工单动作同源（**服务端重新判定一切**）：

| 客户端能送来的东西 | 服务端在哪里重新判定 | 依赖客户端自述？ |
| --- | --- | --- |
| 执行者身份 | **包里根本没有这个字段**——取自连接（`ctx.getSender()`） | 否 |
| 权限 | `PmServerHandlers.onPlayerAction` 第一步就是 `canAdminTicket`（能打开看板 ≠ 有权传送别人） | 否 |
| 「对谁动手」（uuid + 名字） | 在自己玩家列表里**重新解析**：先 UUID、后名字；解析不到就回绝（`player.err.offline`）。两者只是查找线索，不是身份声明 | 否 |
| 动作 id | `PmServerHandlers` 的 `switch` 白名单；未知 id 明确回绝，不静默忽略 | 否 |
| 角色 id | 交给 CCNR-RP 自己解析（`findProfession`）；不存在则该次部署直接失败 | 否 |
| 「有没有 CCNR-RP」 | 由**服务端**回答（`ProfessionListS2C`），不采信客户端装了没装 | 否 |

**UI 上的约束一律不是安全边界**：看板按钮的禁用、菜单的候选项、客户端是否装了某个模组，
都只是为了体验；被改造过的客户端可以把它们全部绕过，而上面每一条都仍然成立。

`PacketRegistrationTest` 把「C2S 包集合」钉死成断言（当前 5 个），并额外断言
**每个玩家动作 id 在服务端都有处理分支**：动作 id 是字符串协议，
漏一个分支编译、单测都不会响，只有管理员点下去才发现「什么都没发生」。

**UI 上的约束一律不是安全边界**：输入框的 `maxLength`、下拉的候选列表、本地的预校验，
都只是为了体验；被改造过的客户端可以把它们全部绕过，而上面每一条都仍然成立。

## 5. 数据模型

```
Ticket
  id            UUID 主键
  id            工单身份（UUID），由存储层分配
  reporterUuid/Name    举报人（名字是快照，便于改名后仍可读）
  targets       关联玩家列表 TicketTarget(uuid?, name) —— 可为空列表（选填）
  categoryId    类别 id（引用 report_categories.json）
  content       举报内容（= /a 那条消息，可编辑，必填）
  detail        详细描述（选填，可含换行）
  status        open | claimed | closed | rejected
  createdAt     创建时间
  handlerName / handledAt / handleNote   受理信息
```

**为什么是「关联玩家」列表而不是单个「被举报玩家」**：一张工单牵涉的往往不止一个人
（动手的、放风的、在旁怂恿的）。做成列表更贴近现实，语义也更中性——它只表示「这张工单和谁有关」，
不预设谁有错。`TicketTarget.uuid` 允许为 `null`（手输的离线名字）。

**DB 结构 v3**：`targets` 单列存 JSON 数组；v1 的两列（`target_uuid`/`target_name`）与 v2 的 `seq` 流水号列均已删除。
v1 **从未对外发布**，因此直接改了列定义而没有写迁移阶梯——日后若 v2 已上线再改结构，**必须**补阶梯。

**标识为什么是 UUID 而不是流水号**：早期版本另有一个「#0001、#0002…」流水号作面向人的编号，
理由是管理员在聊天里方便引用。但它有两个真实缺陷：① **会重复**——序号来自 `max(seq)+1`，
存储被清空或重装（删掉 `tickets.json`、换库）后编号就从 #0001 重新开始，两份数据合并更是必然撞号；② **可枚举**——
看到 #0007 就能推断服务器至今只开过 7 张工单。UUID 两者都没有，因此工单身份**就是** UUID。

显示与输入用它的前 8 位十六进制短号（`#a3f2c1d8`）：完整 UUID 有 36 字符，没法在聊天里口述、也塞不进卡片页眉。
**短号不是身份、只是前缀**——真正的判定永远落在完整 UUID 上，因此
- 命令接受完整 UUID 或 ≥ 4 位短号前缀，**忽略大小写与连字符**；
- 前缀命中多张工单时**报错要求补更多字符**，绝不替用户挑一张（那等于随机认领/办结某张工单）。
相关规则集中在纯类 `TicketId`，由 `TicketTest` 覆盖。
**证据完整性**：状态迁移通过 `Ticket.withStatus` **只改状态与受理字段**，举报原文与描述永不被改写
（`TicketTest.withStatusPreservesContent` 固定了这一约束）。

### 状态迁移

```
open ──claim──► claimed ──close──► closed
  │                 │
  └─────reject──────┴────────────► rejected
```

`claim` 只允许从 `open` 出发，`resolve` 只允许从「未办结」状态出发，
因此两位管理员同时认领同一条时，后者会失败而不是互相覆盖。

## 6. 存储后端

| 后端 | 何时使用 | 位置 |
| --- | --- | --- |
| **JSON 文件**（默认） | `db.enabled=false` 或数据库连不上 | `world/ccnr_pm/tickets.json` |
| **SQLite** | `db.mode=sqlite` | `config/ccnr_pm/ccnr-pm.db` |
| **MySQL** | `db.mode=mysql` | 远端 |

配置文件 `config/ccnr_pm/db.properties`（首次启动不会自动创建，需手动放置或用模板内容）：

```properties
db.enabled=false
db.mode=sqlite
db.file=config/ccnr_pm/ccnr-pm.db
db.host=localhost
db.port=3306
db.database=ccnr_pm
db.user=ccnr
db.pass=
```

### 关键取舍

1. **默认关闭数据库**。单人服/中小服零部署即可用；要 SQL 查询与备份才打开。
2. **连不上就回退文件，而不是静默丢数据**。这是相对 CCNR-RP 的一处刻意改进：
   那里的 `Database.enabled()` 返回的是**配置开关**而非**连接是否成功**，
   于是 `db.enabled=true` 但连接失败时，写操作会静默失败。本模组把二者分开：
   `enabled()` = 配置开关，`usable()` = 开关 **且** 已连接，**所有存储选择都用 `usable()`**。
3. **连库前先建目录**。SQLite 驱动不会自建父目录，`config/ccnr_pm/` 不存在时直接连接失败。
4. **JSON 后端写入失败会回滚内存条目**。否则会出现「面板说成功、重启后消失」。
5. **边界**：JSON 后端是整表常驻内存，适合万级以下工单。更大规模请启用数据库
   （代码里超过 10 万条会截断载入并记 ERROR）。

### 表结构

```sql
CREATE TABLE IF NOT EXISTS pm_tickets (
  id TEXT PRIMARY KEY, reporter_uuid TEXT, reporter_name TEXT,
  target_uuid TEXT, target_name TEXT, category TEXT, content TEXT, detail TEXT,
  status TEXT, created_at INTEGER, handler TEXT, handled_at INTEGER, handle_note TEXT
);
CREATE INDEX IF NOT EXISTS pm_tickets_status_idx ON pm_tickets (status, created_at);
```

**标识分配**：`insert` 直接生成 UUID。改用 UUID 之后，原先「事务内取 `MAX(seq)+1` 再插入」
那段逻辑与唯一序号索引**都不需要了**——少一处并发争用，也少一处可能重复的来源。

**按标识查询会去掉存储侧的连字符再比较**（`REPLACE(id,'-','')`，SQLite 与 MySQL 都支持）：
否则玩家粘贴 32 位无连字符形式、或前缀跨过第 8 位后的连字符时会查不到。
代价是这条查询用不上主键索引——工单量级下可忽略，换来的是「怎么粘都能查到」。

> **迁移边界**：目前只支持 `CREATE TABLE IF NOT EXISTS`。**给已有表加列尚不支持**，
> 若日后要改列结构，必须在 `DbSchema` 新增「读 `pm_schema_version` → 版本低于 N 则 ALTER」的阶梯。

## 7. 配置项

### `world/serverconfig/ccnr_pm-server.toml`

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `report.maxContent` | 256 | 举报内容长度上限 |
| `report.maxDetail` | 512 | 详细描述长度上限（**0 = 禁用该栏**，控件保留但不可编辑） |
| `report.cooldownSeconds` | 60 | 两次提交的冷却（0 = 不限） |
| `report.maxOpenPerPlayer` | 3 | 同时未办结工单上限（0 = 不限） |
| `report.notifyAdmins` | true | 新工单是否私聊提醒在线管理员 |
| `admin.listPageSize` | 10 | 工单列表每页条数 |

长度为 0 时**不是让整栏消失**，而是把输入框置为不可编辑——栏位突然消失会让人以为界面坏了。

### `config/ccnr_pm/report_categories.json`

```json
{
  "categories": [
    { "id": "chat_abuse", "order": 10, "enabled": true },
    { "id": "custom", "order": 70, "enabled": true, "name": "自定义类别" }
  ]
}
```

- 显示名优先取 `name` 字段（字面量，语言中立）；未提供时取语言键
  `ccnr_pm.category.<id>.name`。
- 文件缺失时自动写出模板；文件损坏/无有效条目时回退**内置六类**并记 WARN。
- `enabled=false` 只是「不再接受新工单」，历史工单仍能正常显示该类别名。
- 改完用 `/pm reload` 热重载，不需要重启。

## 8. 命令

| 命令 | 权限 | 说明 |
| --- | --- | --- |
| `/report` | 所有人 | **独立命令**，直接打开举报面板（不必先打 `/pm`） |
| `/pm report` | 所有人 | 同上，`/pm` 下的入口 |
| `/pm ticket list [状态] [页码]` | `ccnrpm.admin.ticket` 或 OP≥2 | 列出工单 |

| `/pm ticket reject <工单号> [备注]` | 同上 | 驳回（并私聊告知举报人） |
| `/pm ticket ignore <工单号>` | 同上 | **忽略**该工单（只影响你自己的看板，不改变工单状态） |

## 9. 排查指南

| 现象 | 先查什么 |
| --- | --- |
| 玩家执行 `/a xxx` 仍提示无权限 | `/pm status` 看「管理通讯权限节点」是否为「已解析」；再看日志里有没有 `[CCNR-PM] 未发现 /a 命令`（表示 CCNR-Com 未装或被更晚注册的同名命令覆盖） |
| 面板打开了但类别是空的 | `config/ccnr_pm/report_categories.json` 是否所有项都 `enabled=false`；`/pm reload` 后再看 |
| 面板打开了但玩家列表是空的 | 服务端此刻确实没有别的在线玩家（自己也已从候选里排除） |
| 提交总说「该玩家已经不在线了」 | 名单是开面板时的快照；对方中途下线是**预期内**的拒绝，重开面板即可 |
| 提示「工单系统尚未就绪」 | 服务端未走完 `ServerAboutToStartEvent`，或 `TicketService.init` 失败（看启动日志的存储后端一行） |
| 明明开了数据库却写在文件里 | 这是**有意的降级**：连接失败时回退文件。日志里会有 `数据库连接失败（将回退文件存储）` |
| 工单标识重复 | 不应发生（UUID）。若发生请保留日志，属严重缺陷 |
| 通知卡片上头像位置是灰块 | 先跑 `/pm status` 看「头像缓存 / 抓不到 / Mojang 反查」三行。日志找 `GameProfile 不含 textures 属性`（纯离线且无皮肤方案）或 `在 Mojang 查不到皮肤`（盗版名）。装皮肤插件（SkinsRestorer 一类）、自建皮肤站，或确认 `avatar.mojangLookup` 开着（正版名可回查 Mojang） |
| 提交时说「找不到玩家 X」 | 该名字既不在线、也不在本服名录里（v0.11.0 起才校验）。让玩家先确认对方名字；对方登录过一次即入名录 |
| 日志出现 `下载头像失败` | 服务端到皮肤站不通（网络/防火墙/皮肤站限 UA）。玩家名与 URL 就在同一条日志里 |
| 卡片迟迟不出现 | 头像抓取有 `timeoutMs`（默认 3s）上限，到点即发。若始终不出，检查 `notifyAdmins` |
| **整合包里面板的输入框「点得亮却打不进字」** | 按顺序查：① 日志里有没有 `[CCNR-PM] 举报面板收到了字符但没有任何输入框接收它`——有，说明字符事件根本没到输入框（看同一行报的焦点类名：`null` = 焦点不在任何输入框上）；**一条都没有**，说明字符事件在到达界面之前就被吃了（见下）。② 「输入法冲突修复(IMBlocker)」类模组按**焦点控件类名**决定是否激活输入法：本模组的胶囊框是自绘控件，不在它的识别名单里，需要把界面类名加进它的 `screenWhitelist`（如 `com.ccnrcom.pm.client.TicketScreen`）或打开 `enableScreenRecovering` 先记录再挑。③ 界面接管类模组（FancyMenu 等）会按界面名套用「通用布局」：聊天栏在它的黑名单里、举报面板不在，所以「聊天能打字、面板不能」是**正常现象**，把本模组的界面加进对应黑名单即可对照验证。④ 最后才怀疑本模组：`charTyped` 只发给 `getFocused()`，焦点若指向已被重建掉的旧控件，症状与此完全一致（0.12.0 已在 `init()` 里把焦点搬到新控件上） |

## 10. 头像缓存（面向第三方服务器）

**问题**：本模组面向第三方服务器，多数是离线验证。离线 UUID 在 Mojang 皮肤库里查无此人，
**客户端自己根本解析不出真实头像**——它只会拿到默认皮肤。

**解法**：服务端在建单前主动抓取皮肤，并随通知一起下发。

```
玩家登录 → AvatarService.prefetch(该玩家)          预热（异步 HTTP）
建单     → 主线程构造 PlayerRef 快照（含 textures 属性）
         → 异步抓取缺失的（≤ timeoutMs）
         → 回主线程把已缓存头像塞进 TicketNoticeS2C
         → 客户端 AvatarTextures 把 base64 注册成动态贴图并绘制
```

| 环节 | 说明 |
| --- | --- |
| 皮肤 URL 来源 | 玩家 `GameProfile` 的 `textures` 属性 → base64 JSON → `textures.SKIN.url` |
| URL 安全 | **只放行 http/https**（`SkinUrl.isHttpUrl`）。否则一个 `file:` URL 就能让服务端去读本机文件 |
| 下载校验 | 状态码 200、≤ 64 KB、PNG 魔数（防止把错误页当皮肤缓存） |
| 缓存语义 | 全局共享、**新的覆盖旧的**（换皮肤后下次抓取即生效）；容量 200 条，超出按抓取时间淘汰 |
| 持久化 | `config/ccnr_pm/avatars.json`（原子写，30s 节流），重启后不必重抓 |
| 失败处理 | 记为 negative，**不反复重试**；卡片回退到客户端本地皮肤 |
| 超时 | 默认 3s；**到点就用已有头像发卡片**，绝不因为皮肤站慢而卡住提醒 |
| 客户端 | base64 → `NativeImage` → `DynamicTexture` → 绘制；卡片消失时 `release`（防 GPU 资源泄漏） |

**边界（重要）**：`textures` 属性由**服务端**填充，因此
- 正版验证 / 装了皮肤插件 / 自建皮肤站 → 能拿到真实头像
- 纯离线且无任何皮肤方案 → 服务端没有这个信息；**v0.11.0 起会按玩家名回查 Mojang**
  （`avatar.mojangLookup`，两步 HTTP：名字→档案、档案→textures）：
  正版名因此也能拿到真实头像，盗版名查不到（记一次负缓存，不再重试），卡片再回退到客户端解析的皮肤。

**排查入口**：`/pm status` 输出「头像缓存：N 条 · 抓不到 M 人 · Mojang 反查 ON/OFF ｜ entries… file… exists…」，
一眼能分辨是「根本没抓到」还是「抓到了但没下发」。

## 11. 管理员通知的两条通道

| 通道 | 形态 | 特点 |
| --- | --- | --- |
| 聊天消息 | `[工单] #a3f2c1d8 Alice 举报 Bob（作弊 / 外挂）` | **持久**、可回滚阅读 |
| HUD 卡片 | 左上角 4:3 横版，12s 后淡出 | **即时**、不打断操作 |

两条一起发是刻意的：管理员正低头挖矿时很容易整条错过聊天，而聊天又是唯一能事后回看的地方。
`report.notifyAdmins=false` 会**同时**关掉两条通道。

## 12. 未做 / 已知边界

1. **在线玩家名单是打开面板时的快照**，不做实时推送。理由：提交时服务端会重新核对，
   快照过期只会导致一次「请重新选择」的拒绝，而为此维护一个增量同步通道不划算。
2. **工单面板只做提交，不做查看**。玩家查看自己的工单历史尚未实现（数据已具备，缺界面与命令）。
3. **无附件/截图**。需要图片证据时应另开设计（涉及素材库与传输通道）。
4. **无回收站**。`closed`/`rejected` 之后不可撤销（数据仍在库里，可人工改）。
5. **举报对象限在线玩家**，这是需求明确要求的（离线玩家无法从下拉里选）。
6. **JSON 后端无并发保护跨进程**：同一份 `world/` 目录被两个服务端同时挂载不受支持。
7. **头像随缓存而非随工单**：按「全局共享、新覆盖旧」实现，因此翻旧工单看到的是**当前**头像而非当时的。
8. **HUD 卡片只在没有打开任何界面时绘制**（原版行为）。管理员开着背包看不到卡片，但聊天提醒仍在。
9. **卡片不能点击关闭**，只能等它淡出（HUD 浮层拿不到鼠标事件）。
